# 2026-10-15 EFI Quadro 源 override 接入

依据用户提供的 `NVPermissiveEFI-202610150835.efi`，SHA256
`2bf6c06346ccdbdb0deba7ff6e0d423c08991b5f20b588302d0563c158c538e3`。
PE `.core` 从文件偏移 `0xbe00` 开始，包含可重定位 AMD64 ELF，版本字符串为
`core 4c32b72 built 2026-10-15 08:35:29`。以下偏移均相对于嵌入 ELF 的 `.text`。

## 已确认的指令事实

- `0x11bc0`：要求 FEAT PLM `0x823804` **精确等于 `0xffffffff`**。
- 读取源 override `0x823808`，拒绝全一和 `BADFxxxx`。
- `0x11c00`：`and r13d,0xfc6ff444; or r13d,0x03900888`，然后写回 `0x823808`。
- 因此写法为 `next = (old & ~0x03900bbb) | 0x03900888`，保留掩码外位。
- `0x11b10`：回读源寄存器，要求 `(value & 0x03900bbb) == 0x03900888`。
- `0x132dc`：compute 事务在开放权限后调用写入 helper，随后进入原有 handoff；最终验证路径再次校验源 override。
- `0x14bc0`：即使 compute selector 已匹配，也检查 Quadro；源目标未满足时，FEAT 已开可直接补写，FEAT 未开则走完整固件链。
- `0x11750`：读取 `0x823814`，仅作 diagnostic；不能用 READOUT 未达目标或不可读直接替代源 override 成败。

EFI 自身日志将这些字段命名如下；这些名称来自该 EFI，并非独立硬件手册验证：

| 字段 | source value | override | 本次目标 |
| --- | --- | --- | --- |
| SETUP_SMOOTHLINE | bits 1:0 | bit 3 | value=0, override=1 |
| SETUP_POLYMODE | bits 5:4 | bit 7 | value=0, override=1 |
| SETUP_TWOSIDED_LIGHT | bits 9:8 | bit 11 | value=0, override=1 |
| TFQ | bit 20 | bit 23 | value=1, override=1 |
| SM_TTU | bit 24 | bit 25 | value=1, override=1 |

此前实测源值 `0x00100283` 按该公式得到 `0x03900888`。
这份 EFI 的实际写法包含全部五组字段，不能简化为直接写 `0x03000000`。

## 实现和测试入口

Native 的 `native/rebuilt-core/core.c` 在 compute feature stage 成功之后、handoff 之前执行 RMW，
在 handoff 前后验证源目标，保留身份、权限和 DMA 生命周期检查。compute 预检查同时判断 Quadro，
避免旧的 compute-only 快路径漏掉新增功能。Session 使用相同源码，最终整体校验也检查 Quadro。

Native 使用新核心测试包 `build/rebuilt-core/worker-hardware/`，由
`tools/build-rebuilt-core.ps1`、`tools/build-rebuilt-worker.ps1 -EnableHardwareCommands` 生成。
worker 只接受构建时固定的 candidate/research 哈希；原有固定核心不因此获得 Quadro 写入功能。
新的驱动必须与测试 worker 的调用者哈希匹配，使用 `tools/build-rebuilt-driver.ps1` 生成配套包，
签名后才能由用户加载。Console 的 backend 包仍需按既有流程复制完整配套签名包并刷新哈希。

不访问硬件的独立测试命令（测试 worker）：

```powershell
./CMP90HXUnlocker.exe quadro-test --core ./nvpermissive-core.o
```

该命令直接加载最终 source-only 核心，在模拟 MMIO 上执行 1000 组 RMW 及失败路径测试。
测试包和 Console 输入目录中的核心文件统一使用 `nvpermissive-core.o`。
`build/rebuilt-core/nvpermissive-rebuilt-hybrid.o` 是构建中间产物，打包时以固定文件名复制，内容和哈希不变。
完整硬件解锁仍使用既有 `full-unlock` 流程；普通物理 DMA 路径要求显卡已停用 Code 22，
并预先加载与测试 worker 配套的已签名驱动。

Console 显示“光追 / Quadro：已设置”，含义仅为源 override 达到掩码目标。
共享 reader 在固定 64 字节结构的 reserved[0]/[1] 返回源值和 READOUT，Flags bit1 标记字段存在；
新版 client 可读取旧 driver，但不将旧包缺失字段当零值或成功。

静态证据可复现：

```powershell
python tools/inspect-rt-efi.py ../NVPermissiveEFI-202610150835.efi --out build/rt-efi-evidence --capstone-path PATH_TO_CAPSTONE
```

测试覆盖源码状态机、随机 RMW 的无关位保留、已匹配幂等路径、不可读源值、写入回读失败、
复位后目标丢失、事务 DMA 保留，以及 worker 中实际 ELF 的 Quadro 快路径。
静态与模拟测试不能证明 DXR 工作负载正确或 RT 硬件性能恢复；需要在同一驱动/设备状态下另行验证。
